# Notes for working in this component

A dbt project transforming `els-database`'s raw `els` schema into a dimensional model (dimensions/facts) in the same SQL Server database. See the repo root `CLAUDE.md` for conventions that apply repo-wide.

## Conventions specific to this component

- **Folder and dbt project name (`els_transform`) use underscores, not hyphens** like every other component. dbt requires a project's `name:` to be a valid identifier (letters/digits/underscores only) — the folder matches it exactly rather than tracking two different names. Don't rename this folder to match the hyphenated convention elsewhere; that would break the dbt project name too.
- **Target platform: the same SQL Server instance `els-database` deploys to, not a separate warehouse.** Decided explicitly (see `docs/els-transform.md`) — dbt only transforms data already in one database, so a different target (e.g. Snowflake) would have required a whole separate extract/load component first.
- **Adapter: `dbt-sqlserver` (the community-maintained `dbt-msft` adapter), not dbt's Fusion engine.** Checked directly, not assumed: Fusion's supported adapters (Snowflake, BigQuery, Databricks, Redshift — all "Preview") don't include SQL Server as of this decision. This also rules out dbt Labs' own official VS Code extension, which requires Fusion regardless of registration status. Use `sqlfluff` with the `dbt` templater for editor linting instead — it works against plain dbt-core with any adapter.
- **`.sqlfluff` lives in this folder, not the repo root.** It's config for this dbt project specifically — its `project_dir`/`profiles_dir` settings are simplest when it sits next to `dbt_project.yml` — and a repo-root config would technically also apply to `els-database`'s plain, non-templated T-SQL files, which sqlfluff's `dbt` templater has no business touching.
- **`profiles.yml` is intentionally not part of this repo**, same "never commit real connection info" rule as `els-database/config/`. Unlike that component, there is currently no committed `profiles.template.yml` showing a fresh clone what shape is expected — worth adding once the `dbt-sqlserver`-specific keys (`driver`, `encrypt`, `trust_cert`, etc.) are settled, mirroring `els-database/config/config.template.json`'s pattern. Don't invent one speculatively without checking the adapter's actual required keys first.
- **Models are hand-authored directly, not generated.** Unlike `els-database`'s `generate-full-schema`, no tool derives these `.sql` files from `els-data-model` — the dimensional design is owned directly. This file (and the README) document the project's shape and tooling, not its dimensional design; don't add, remove, or restructure anything under `models/` on the basis of this file alone.
- **`seeds/` is dbt's own mechanism** (static CSVs loaded as tables via `dbt seed`) — a different thing entirely from `els-data-model/data/*.json`, which is that component's hand-authored reference data. Don't conflate the two if `seeds/` ever gets used for real.
- **`target/` and `logs/` are dbt's own build output.** Regenerated by every `dbt run`/`dbt compile`, gitignored, never hand-edited or committed.
- **Orchestration: none automated yet, and won't be until the reachability question is settled.** The SQL Server this targets is a local install on Karel's own machine — a GitHub-hosted Actions runner cannot reach it. The planned path is manual `dbt build` while models are actively being built, moving later to a self-hosted GitHub Actions runner on that same machine (keeps CI defined as code, matching the repo's GitHub-Actions default, without relocating the database). dbt Cloud was considered and rejected for the same reachability reason — see `docs/els-transform.md`.
- **No `packages.yml` yet.** If `dbt_utils` (e.g. `generate_surrogate_key()`) or any other dbt package becomes needed, add `packages.yml` and run `dbt deps` — don't hand-roll what a well-known package already does.
- **The default `generate_schema_name` macro concatenates a model's `+schema:` config onto the profile's default target schema** (e.g. `+schema: dw` becomes `dbo_dw`, not `dw`) — a well-known dbt surprise, not yet worked around here. If/when staging and marts need separate schemas, add a `macros/generate_schema_name.sql` override using dbt's own documented pattern rather than rediscovering this the hard way.

## Out of scope here

This file intentionally says nothing about which dimensions/facts should exist, their grain, or surrogate-key strategy (hash-based via `dbt_utils.generate_surrogate_key()` vs. passing the source system's own integer keys through directly — both are legitimate for a single-source star schema like this one; that's active modeling work, decided model by model, not a build/tooling convention captured here.

## Verifying changes

No CI wired up yet. Locally: `dbt debug` checks the profile/connection without changing anything; `dbt run` or `dbt build` actually builds; `sqlfluff lint models/` once the `sqlfluff` CLI, `sqlfluff-templater-dbt`, and a VS Code extension surfacing its output are installed per the README's Linting section.
