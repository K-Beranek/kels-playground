# eLearning System Transformation (`els_transform`)

A [dbt](https://www.getdbt.com/) project that transforms the fictional eLearning System's raw operational data into a dimensional model — dimension and fact tables — for reporting/analytics. This component owns the transformation logic only: [`els-database`](../els-database/) owns the physical `els` schema it reads from, and [`els-data-model`](../els-data-model/) owns the entity definitions that schema was generated from.

## Why this folder uses underscores, not hyphens

Every other component in this repo is hyphenated (`els-data-model`, `els-database`). This one isn't, because dbt requires it: a dbt project's `name:` in `dbt_project.yml` must be a valid identifier — letters, digits, and underscores only, no hyphens — and this folder is named to match that project name exactly rather than tracking two different spellings of the same thing. Not an inconsistency, a constraint from the tool.

## Layout

```
els_transform/
├── dbt_project.yml       dbt project configuration (materializations, file paths)
├── .sqlfluff             sqlfluff config using the dbt templater — see "Linting" below
├── models/
│   ├── staging/          Thin, ~1:1 cleanup views over els-database's raw els.* tables
│   └── marts/            The actual star schema: dimension and fact models
├── macros/               Custom Jinja macros (none yet)
├── seeds/                dbt's own CSV-seed mechanism (none yet — see CLAUDE.md for how this
│                         differs from els-data-model's data/*.json seed data)
├── snapshots/            dbt snapshots for slowly-changing data (none yet)
├── tests/                Custom/singular dbt tests, beyond the column-level tests in each
│                         models/*/*.yml (none yet)
├── analyses/             Ad-hoc queries dbt compiles (for ref()/source() resolution) but
│                         never runs as models (none yet)
└── target/, logs/        dbt's own build output and logs — gitignored, regenerated every run
```

Models — the actual dimension/fact SQL — are designed and written directly, not generated by any tool the way `els-database`'s schema is. This README documents the project's shape and setup, not its dimensional design.

## Setup

**Target platform.** The star schema lands in the same SQL Server instance `els-database` deploys to — a deliberate choice over a separate warehouse (e.g. Snowflake), made explicitly rather than assumed. dbt only transforms data already sitting in one database; it never moves data between platforms itself. Targeting Snowflake instead would have meant building a whole separate extract/load component first, since the source data lives in SQL Server. See [`docs/els-transform.md`](../docs/els-transform.md) for the full trade-off.

**Install dbt.** This project uses the community-maintained `dbt-sqlserver` adapter, not dbt's newer Fusion engine — Fusion's currently-supported adapters (Snowflake, BigQuery, Databricks, Redshift, all still "Preview") don't include SQL Server.

```bash
pip install dbt-core dbt-sqlserver
```

`dbt-sqlserver` uses `pyodbc` under the hood, so it needs the same OS-level ODBC driver `els-database/scripts/generate-synthetic-data` already documents (`ODBC Driver 18 for SQL Server`) — no new OS dependency if that's already installed.

**Connection details.** `profiles.yml` is intentionally not part of this repo — same "never commit real connection info" rule as `els-database/config/`. dbt looks for it at `~/.dbt/profiles.yml` by default. There is currently no committed `profiles.template.yml` documenting its expected shape (unlike `els-database/config/config.template.json`) — a gap worth closing once the `dbt-sqlserver`-specific keys are settled.

**Packages.** No `packages.yml` yet — nothing here depends on `dbt_utils` or any other dbt package so far. Add one (and run `dbt deps`) if that changes, e.g. for `generate_surrogate_key()`.

**Run it**, from inside this folder:

```bash
dbt debug   # checks the profile/connection without running anything
dbt run     # builds all models
dbt build   # builds all models AND runs their tests
```

## Linting

`.sqlfluff` (in this folder's root, not the repo root — see `CLAUDE.md` for why) configures sqlfluff's `dbt` templater, so it actually renders each model's Jinja (`ref()`, `source()`) through this real dbt project before linting the resulting SQL, rather than just recognizing the Jinja syntax shape. dbt Labs' own official VS Code extension does **not** work for this project — it requires the Fusion engine, which doesn't support SQL Server — so `sqlfluff` plus a generic Jinja-aware syntax highlighter is the practical substitute for inline editor diagnostics here.

## Status

Scaffolded via `dbt init`. Two example models exist so far, both hand-authored: `models/staging/stg_els__campus.sql` (a cleanup view over `els.campus`) and `models/marts/dim_campus.sql` (selects from the staging model) — both have compiled and run successfully against a live database. See [`docs/els-transform.md`](../docs/els-transform.md) for the broader decisions log.
