# Review: eLearning System Data Model (`els-data-model`)

## What it is

The foundation component: entity definitions (Campus, Course, CourseType, StudyProgram, SemesterType, CurriculumType, Semester, Term, TermCourse, Person, CourseContentType, CourseContent, CourseTest, CoursePersonRole, CoursePerson, Submission), a Mermaid ER diagram, a machine-readable schema per entity, and synthetic seed data. Nothing here executes — it's a source of truth other components read.

## Key decisions

- **Custom JSON format for entities, not DBML.** DBML already has libraries that turn it into DDL directly, which would make the eventual DDL-generation component trivial rather than a real exercise. A small purpose-built format keeps that future work meaningful.
- **JSON Schema used for validation, not for the model itself.** JSON Schema has no native concept of primary/foreign keys, so it wasn't a good fit as the *model* format — but it's the right tool to validate the custom format's structure, so `model/schema/model.schema.json` fills that role.
- **Abstract, dialect-independent types.** Column types (`integer`, `string`, ...) intentionally don't map to any specific database's type system. That mapping is future work for whatever component generates DDL for a specific target (e.g. Snowflake vs. SQL Server).
- **Single-column identity primary keys, not composite.** `Course` originally used a composite key (`campus_id`, `id`) to exercise that case deliberately; it was later changed to a single `id` identity column (database-generated, unique system-wide), with `campus_id` demoted to a plain foreign key. The format still supports composite keys (order of `primaryKey: true` columns in the array = key order) — it's just not exercised by either current entity anymore.
- **`identity` is schema-enforced alongside `nullable`.** A column can't be `identity: true` and `nullable: true` at once (SQL Server wouldn't allow it) — the JSON Schema itself rejects that combination via an `if`/`then` rule, and `els-database`'s generator checks it again before emitting DDL, so a mistake here is caught at two independent layers.
- **`description` renamed to `comment`** for the entity/column-level documentation field, to avoid ambiguity with the fact that both entities also have an actual column literally *named* `description`. The rename only touched that metadata key — the real `description` column, and all seed data, were untouched.
- **Composite uniqueness via `uniqueWith`, kept separate from the existing `unique` boolean.** When `Course.course_number` needed to be unique per-campus rather than system-wide, the option considered first was overloading `unique` itself (boolean → string, presence/value both carrying meaning) — rejected in favor of a second, purpose-specific field (`uniqueWith: ["campus_id"]`) so `unique`'s meaning never depends on its value's content, and every existing standalone-unique column needed no migration. The two are mutually exclusive on one column, enforced structurally by the JSON Schema (same `if`/`then` pattern as `identity`/`nullable`); a `uniqueWith` entry naming a column that doesn't exist on the entity is a check the JSON Schema can't practically express (it would need to cross-reference sibling array entries by name), so that one lives only in `els-database`'s generator.
- **`CourseType` is the model's first lookup table**, added as a standalone reference table (`code`, `display_name`, `sort_order`, `is_active`), now linked to `Course` by a foreign key (`Course.course_type` → `CourseType.code`). `display_name` is independently `unique`, deliberately kept separate from `code`: `code` (`IN_PERSON`, `ONLINE`, ...) is a stable machine key for application code/integrations, `display_name` is the human-readable GUI label, and they're expected to be able to change independently of each other (e.g. rewording a label without touching anything that keys off `code`). `sort_order` and `is_active` follow the general lookup-table design discussed for this repo (see `CLAUDE.md`'s reusable patterns): explicit presentation order rather than relying on `code`/alphabetical order, and a way to retire a value from new selections without invalidating rows that already reference it.
- **`Course.course_type` is a foreign key to a natural key, not a surrogate one.** This is the model's first FK whose target column isn't an `identity` primary key — `foreignKey: { entity: "CourseType", column: "code" }` names the target column explicitly rather than assuming `id`, which is what let this work with no format or generator changes (see `els-database`'s review doc for the generator-side confirmation). Nothing about the FK itself is unusual; only its target shape is.
- **`CourseType.code` is the primary key directly — no separate surrogate `id`.** Built with one initially (surrogate `id`, plus `code`/`display_name`/`sort_order`/`is_active`), then deliberately removed once it became clear it would sit unused: `code` already *is* the entity's natural, stable identifier, so a surrogate `id` alongside it would just be a second, redundant key — application code would end up keying off the meaningless `id` while `code` (the column actually designed for that) went unreferenced. `Campus` and `Course` keep their surrogate `id`s, since neither has an equally natural, guaranteed-unique alternative sitting right there — this is a deliberate case-by-case call, not a rule that lookup tables never get surrogate keys.
- **`Campus.uuid` — a stable external identifier alongside the internal `id`.** Modeled as a plain `string(36)`, not a dedicated UUID/GUID abstract type (the model's type system doesn't have one), so it renders as `NVARCHAR(36)` rather than SQL Server's native `UNIQUEIDENTIFIER`. That's a deliberate scope choice for now, not a rejection of `UNIQUEIDENTIFIER` — worth revisiting if this component ever wants a real "GUID" abstract type with per-dialect mapping.
- **Academic scheduling entities added as a set: `StudyProgram`, `SemesterType`, `CurriculumType`, `Semester`, `Term`, `TermCourse`.** `StudyProgram` and `Semester` follow `Course`'s established "campus-scoped natural code" shape (`uniqueWith: ["campus_id"]` on `code`), rather than introducing a new pattern. `SemesterType` and `CurriculumType` are two more lookup tables of exactly `CourseType`'s shape (natural `code` primary key, `display_name`, `sort_order`, `is_active`) — no new lookup-table variant was invented, the existing pattern was just reused twice more. `Term` and `TermCourse` are the first entities with no `code`/`name` of their own — they're pure linking entities, identified only by the combination of what they reference (`Term`: campus + study program + semester; `TermCourse`: campus + term + course + curriculum type).
- **`campus_id` is deliberately added to every entity holding per-campus data, not just where a foreign-key chain already reaches a campus.** `Course`, `StudyProgram`, `Semester`, `Term`, and `TermCourse` all carry their own `campus_id`, even where it's technically redundant (`Term.campus_id` is also reachable via `study_program_id` or `semester_id`; `TermCourse.campus_id` via `term_id` or `course_id`). This is intentional, not an oversight: the goal is to be able to tell which campus a row "belongs to" by reading the row itself, with no join needed — the kind of thing that matters for row-level filtering or access control scoped by campus. See the "Campus scoping" section of `els-data-model`'s own README for the full reasoning.
- **`campus_id` cross-table integrity is explicitly out of scope for now, not silently assumed.** Denormalizing `campus_id` onto every campus-scoped table creates a real integrity rule this model doesn't enforce: when a row references two or more other rows that each carry their own `campus_id` (e.g. `TermCourse.term_id` and `TermCourse.course_id`), all of those need to actually agree with each other and with the row's own `campus_id` — a `TermCourse` should never be able to reference a `Term` and a `Course` from two different campuses. Nothing in the JSON entity format, the JSON Schema, or `els-database`'s generator can express or check this; it's a genuine cross-table constraint, which a single-table `CHECK` can't cover — real enforcement would need a trigger or application/service-layer validation. For now this is a known, explicitly-scoped-out gap: the seed data was built and hand-verified to be consistent, but nothing in the system guarantees it stays that way, and maintaining that consistency for any new data is a manual discipline until this gets real enforcement.
- **`Term` and `TermCourse` gained composite uniqueness on their natural combination of foreign keys.** `Term.semester_id` is now `uniqueWith: ["campus_id", "study_program_id"]` (`UNIQUE (campus_id, study_program_id, semester_id)`): a study program can't have two terms in the same semester at the same campus. `TermCourse.course_id` is now `uniqueWith: ["campus_id", "term_id"]` (`UNIQUE (campus_id, term_id, course_id)`): the same course can't be scheduled twice into the same term. This closes the "duplicate row" gap flagged when these entities were first added — it's a genuinely different concern from the `campus_id` cross-table integrity gap above (this catches a repeated combination on one table; that one is about the same `campus_id` value being honest across several tables) and required no format or generator changes, just reusing `uniqueWith` exactly as `Course.course_number` already does.
- **`Campus` gained a `code` column: a third, distinct kind of identifier alongside `id` and `uuid`.** `id` is a stable internal surrogate but not meant to be typed or remembered; `uuid` is stable and external-facing but far too long to remember; `code` is a short, human-memorable static string (e.g. `"MAIN"`). It's a standalone `unique: true` column, not `uniqueWith` — unlike `Course.course_number` or `StudyProgram.code`, `Campus` has no parent entity to scope uniqueness within, so `code` is unique system-wide by construction, the same way `uuid` already is. This is the model's first *new column on an entity that already has both seed data and several downstream referencing entities* (`Course`, `StudyProgram`, `Semester`, `Term`, `TermCourse` all carry a `campus_id` FK) — worth noting that adding a plain non-FK column to `Campus` has no ripple into any of those referencing entities at all; only a change to what `Campus` is *keyed by* would.
- **A learning/assessment slice added as a set: `Person`, `CourseContentType`, `CourseContent`, `CourseTest`, `CoursePersonRole`, `CoursePerson`, `Submission`.** `Person` reuses `Campus`'s `id` + standalone-unique `uuid` shape; `CourseContentType` and `CoursePersonRole` are two more `CourseType`-shaped lookup tables. `CourseTest.code` introduces a variant of the "natural code, unique within a scope" pattern already used by `Course.course_number`/`StudyProgram.code`/`Semester.code` — but scoped by `course_id` (`uniqueWith: ["course_id"]`), not `campus_id`, since a test's natural scope is the course it belongs to, not the campus. `CoursePerson.person_id` (`uniqueWith: ["campus_id", "course_id"]`) and `Submission.attempt_number` (`uniqueWith: ["campus_id", "course_person_id", "course_test_id"]`) are further reuses of the same composite-uniqueness mechanism `Term`/`TermCourse` already exercise, this time on association/attempt entities.
- **`document_text`, `test_questions`, and `submission_text` are bounded `string(4000)`, not the unbounded `text` type.** This is the model's first deliberate use of a capped string length for a "long free text" column rather than defaulting to `text` (`NVARCHAR(MAX)`) the way `Campus.description`/`Course.description`/`StudyProgram.description` do. 4000 is SQL Server's largest `NVARCHAR` size that isn't `MAX` — a real, common trade-off (indexing and some operations behave differently on `MAX` columns) that this model can now represent, since `string` already supports an arbitrary `length`.
- **`CourseContent` gained a `course_id` foreign key.** Built without one initially (implemented literally as specified, then flagged as unusual for this kind of entity); Karel confirmed a content item does belong to a specific course, and `course_id` was added right after `campus_id`, matching the FK-ordering convention already used elsewhere (business FK, then lookup FK, then `id`). No uniqueness constraint ties `course_id` and `content_type` together — a course can have any number of content items of the same type, unlike e.g. `CourseTest.code`'s per-course uniqueness.
- **`Submission` carries a second, more indirect version of the `campus_id` cross-table integrity gap.** `Submission.course_person_id` and `Submission.course_test_id` each resolve (through `CoursePerson.course_id` and `CourseTest.course_id`) to a course, and those two courses are expected to always match — a submission's course-person and course-test should be for the same course. This is explicitly not enforced, the same way `campus_id` consistency across a row's foreign keys isn't enforced — noted directly in `Submission.course_test_id`'s `comment` field, and confirmed against the actual seed data (which was built consistent by hand, same discipline as the `campus_id` case).

## How other components should use this

- Treat `model/entities/*.json` as read-only input, not something to fork or reinterpret. If a component needs an entity that doesn't exist yet, add it here first.
- A DDL-generation component (not yet built) is expected to read `model/entities/*.json` and emit `CREATE TABLE` statements per target dialect, resolving the abstract types and composite keys described above.
- `data/*.json` is meant for seeding — loading it into a real database once one exists, for other components (ETL, reporting, etc.) to have something to work against.

## Deployment

Nothing to deploy — this component is static definition files, consumed by other components rather than run on its own.

## Status

In progress. Sixteen entities defined (Campus, Course, CourseType, CurriculumType, Semester, SemesterType, StudyProgram, Term, TermCourse, Person, CourseContentType, CourseContent, CourseTest, CoursePersonRole, CoursePerson, Submission). Most use single-column identity primary keys; CourseType, SemesterType, CurriculumType, CourseContentType, and CoursePersonRole are lookup tables keyed on a natural `code` column rather than a surrogate `id`. No automated validation/CI wired up yet.

Note on a ripple effect from the `Course` primary-key change: `id` was previously unique only *within* a campus (part of the composite key), so the seed data reused small id values (`1`) across different campuses. With `id` now the sole, globally-unique primary key, those seed rows were renumbered (`1`–`4`) to stay valid — `campus_id` values were left unchanged. `els-database`'s schema generator was re-run and confirmed to still produce deterministic, correctly-constrained output against the updated model.

A related but separate change: `course_number` moved from a standalone system-wide unique constraint to a composite one with `campus_id` (`uniqueWith`), meaning the same course number is now allowed to exist at two different campuses. The existing seed data needed no changes — all four rows already had distinct `course_number` values, which trivially satisfies the new, looser constraint too.

Adding `Campus.uuid` (`nullable: false`) did require a seed-data update, unlike the `course_number` change above: all three existing `Campus` rows needed a real value added, since a new `NOT NULL` column has no implicit default in this format. `CourseType`'s four seed rows (`In Person`, `Online`, `Hybrid`, `N/A`) were loaded in the requested display order via `sort_order` 1–4, all marked `is_active: true`. `els-database`'s schema generator was re-run against the updated model and confirmed still deterministic (byte-identical re-run, `--check`) with the new column and table folded in — `CourseType` sorts alphabetically after `Course` (not between `Campus` and `Course` — `"Course"` is a prefix of `"CourseType"`, and a prefix always sorts before the longer string it prefixes), landing last in generated output without disturbing `Campus` or `Course`'s existing statements.

`CourseType` was then refactored to drop its surrogate `id` in favor of `code` as the primary key directly — a genuine structural change, so it got the same ripple-effect check as the `Course` primary-key change earlier: seed data updated (the `id` field simply removed from all four rows, since `code` was already present and already correct as the new key), and the schema generator re-run and re-verified deterministic against the new shape. No downstream impact beyond that, since nothing referenced `CourseType` by a foreign key yet at the time — this would have been a more involved change (updating every referencing FK's target column) had one existed.

Adding `Course.course_type` (foreign key to `CourseType.code`, `nullable: false`) needed the same seed-data backfill treatment as `Campus.uuid` earlier: all four existing `Course` rows got a real `course_type` value (`CS101`→`IN_PERSON`, `CS210`→`HYBRID`, `BUS110`→`IN_PERSON`, `DE100`→`ONLINE`), chosen to plausibly match each course's campus and subject rather than picked arbitrarily. This is the first foreign key in the model whose target column isn't an `identity` surrogate primary key, so it doubled as a direct test of the generator's `render_foreign_keys()` — confirmed to build the `REFERENCES` clause from whatever column name the model's `foreignKey.column` names, not an assumed `id`, requiring zero generator code changes. Full regression suite re-run and passed (byte-identical rerun, `--check`, and a synthetic entity insertion confirming `Campus`/`Course`/`CourseType`'s existing statements were untouched).

Six entities added in one pass — `StudyProgram`, `SemesterType`, `CurriculumType`, `Semester`, `Term`, `TermCourse` — bringing the model to a full academic-scheduling slice: campuses offer study programs, semesters happen at campuses, terms tie a program to a semester at a campus, and term courses schedule individual courses into a term with a curriculum type. All new seed data was hand-checked programmatically for referential integrity (every foreign key value resolves to a real row in its target entity) and for the two new campus-scoped uniqueness constraints (`StudyProgram.code`, `Semester.code`, both `uniqueWith: ["campus_id"]`) before the generator was ever run — catching this kind of mistake in the JSON is much cheaper than catching it as a SQL constraint violation later. The schema generator went from 3 tables to 9 with zero code changes (every new shape — campus-scoped natural codes, more `CourseType`-style lookup tables, plain linking entities with no unique business key of their own — was already covered by existing generic logic); full regression suite re-run and passed (byte-identical rerun, `--check`, and a direct diff confirming `Campus`, `Course`, and `CourseType`'s generated `CREATE TABLE` and FK statements were untouched by the six new entities landing around them alphabetically).

Shortly after, `Term` and `TermCourse` picked up the composite uniqueness constraints flagged as a "reasonable next refinement" when they were first built: `Term.semester_id` got `uniqueWith: ["campus_id", "study_program_id"]`, and `TermCourse.course_id` got `uniqueWith: ["campus_id", "term_id"]`. Existing seed data needed no changes — both entities' four rows already satisfied the new, tighter constraints, since the seed data had been built with distinct combinations from the start. Full regression suite re-run and passed (byte-identical rerun, `--check`), and a direct diff against the pre-change output confirmed the only differences were the two new `UNIQUE` constraint lines and their corresponding updated column comments — every other table's `CREATE TABLE`, foreign key, and comment statement was untouched.

`Campus` then gained a `NOT NULL`, standalone-unique `code` column — the same kind of ripple as `Campus.uuid` earlier: since `Campus` already had three seed rows, each one needed a real, distinct value backfilled by hand (`"MAIN"`, `"DOWNTOWN"`, `"ONLINE"`), verified unique before the generator ran. Full regression suite re-run and passed (byte-identical rerun, `--check`), and a direct diff against the pre-change output showed exactly three new lines — the `code` column definition, its `UQ_campus_code` unique constraint, and its column comment — with every other table's statements, including `Course`/`StudyProgram`/etc.'s `campus_id` foreign keys, untouched. Nothing referencing `Campus` needed any change, since none of them reference it by `code` — they all still point at `Campus.id`.

Seven more entities were added in one pass — `Person`, `CourseContentType`, `CourseContent`, `CourseTest`, `CoursePersonRole`, `CoursePerson`, `Submission` — taking the model from 9 to 16 tables and adding its first learning/assessment slice (people, content, tests, course roles, and test submissions) on top of the existing academic-scheduling one. All new seed data was hand-checked programmatically for referential integrity, for the internal uniqueness of the two new lookup tables, and for the three new composite uniqueness constraints (`CourseTest.code` scoped by `course_id`, `CoursePerson.person_id` scoped by `campus_id`+`course_id`, `Submission.attempt_number` scoped by `campus_id`+`course_person_id`+`course_test_id`) before the generator was ever run — the same discipline used for the six-entity academic-scheduling batch. The seed data for `Submission` was also hand-checked against the *unenforced* rule that a submission's `course_person_id` and `course_test_id` must resolve to the same course, even though nothing in the model itself checks this. The schema generator went from 9 to 16 tables with zero code changes — every shape used (more lookup tables, `uniqueWith` scoped by a business FK instead of `campus_id`, a bounded `string(4000)` column, an entity with no FK to a "parent" at all) was already covered by the generator's existing generic logic. Full regression suite re-run and passed (byte-identical rerun, `--check`, and a direct diff confirming all nine pre-existing tables' `CREATE TABLE`, foreign key, and comment statements were untouched — the diff contained only added lines, zero removed or changed ones).

Karel then confirmed that flagged gap was a real omission: `CourseContent` picked up a `NOT NULL` foreign key to `Course`, added right after `campus_id`. The four existing seed rows needed `course_id` backfilled by hand (same kind of ripple as any `NOT NULL` column added to an entity with existing data), each one chosen and hand-verified to match the row's existing `campus_id` — the same discipline already used for `campus_id` consistency elsewhere in this model. Needed no generator code changes: a new plain foreign key on an already-existing entity is exactly the shape `render_foreign_keys()` already handled. Full regression suite re-run and passed (byte-identical rerun, `--check`), and a direct diff against the pre-change output showed exactly three new lines — the `course_id` column, its foreign key constraint, and its column comment — with every other table's statements, and `CourseContent`'s own other columns, untouched.
