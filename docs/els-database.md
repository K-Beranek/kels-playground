# Review: eLearning System Database (`els-database`)

## What it is

The SQL Server side of the fictional eLearning System: Flyway migrations, the script that runs them, and a working area for modeling schema changes. Scaffolded first; real migration content is arriving incrementally — `utils` now has its first stored procedures, `els` still has only a placeholder.

## Key decisions

- **JSON for config, over YAML/TOML/INI.** Chosen because both PowerShell and Python read/write JSON natively with zero extra dependencies, and this repo deliberately mixes scripting languages across components — a format both can use without a library made more sense than one that's nicer to hand-edit (YAML) or thematically matched to Flyway itself (TOML, since `flyway.toml` uses it) but needs extra tooling in at least one of the two languages.
- **PowerShell for the Flyway-calling script, not Python.** PowerShell is the idiomatic tool for Windows + SQL Server ops scripting, and it's an area Karel rated "reasonable" rather than expert — deliberate practice. A Python twin is a natural future addition, consistent with this repo's pattern of building the same thing more than once to compare approaches.
- **Config folder ships only a template.** `config/.gitignore` allowlists just `.gitignore` and `config.template.json`; every real config (with real server names and credentials) is created locally and can never be committed by accident.
- **`full_db_model/wip` is tracked but empty.** Using the `*` + `!.gitignore` pattern inside that folder's own `.gitignore` keeps the folder present in a fresh clone without ever committing what gets dropped into it — useful for a folder that's explicitly meant as local scratch space.
- **Migrations organized per schema** (`migrations/els`) rather than one flat folder, so a second schema later doesn't get mixed in with the first.
- **Flyway runs one schema per invocation, not multiple at once.** `Invoke-ElsMigration.ps1` takes a mandatory `-Schema` parameter (no default, so a run always states its target explicitly) and `config.json`'s `flyway.schemas` became a dictionary keyed by schema name (`{"els": {...}, "utils": {...}}`) instead of a single schema/path pair. This isn't just a config reshape — it's how Flyway itself is meant to handle multiple schemas: each run gets its own `flyway_schema_history` table inside the targeted schema, so `-Schema utils` and `-Schema els` are genuinely independent histories that can be run on independent cadences (utils rarely, els often), rather than something bolted on top of a single shared history.
- **Schema generator lives under `scripts/`, not `full_db_model/`.** `full_db_model/current` and `wip` are documented as data (schema snapshots), and `wip` is deliberately gitignored — putting tracked Python source next to a sibling folder whose whole point is "ignore everything" invited exactly the kind of gitignore-pattern mistake this repo is trying to avoid elsewhere. `scripts/` was already the documented home for "tooling that manages this component's files," so the generator is a subfolder there instead.
- **Determinism by construction, not by convention.** The generator sorts entities by name immediately after loading rather than trusting file-discovery order — a sort's relative ordering of two existing items is mathematically stable under insertion, so a new entity can be added anywhere without ever reordering what's already there. This was tested directly (see Status below), not just asserted.
- **Foreign keys as `ALTER TABLE` after all `CREATE TABLE`s**, specifically to avoid needing to topologically sort tables by dependency.
- **`identity` columns render as `IDENTITY(1,1)`, with the identity+nullable contradiction checked twice** — once structurally by `els-data-model`'s JSON Schema (an `if`/`then` rule), and again by this generator before rendering DDL. Belt-and-suspenders deliberately: catching it at the model layer gives an earlier, clearer error, but the generator doesn't rely solely on the schema having been kept in sync.
- **Unique constraints can be standalone (`unique: true`) or composite (`uniqueWith: [...]`), mutually exclusive on the same column.** Added when `Course.course_number` needed to be unique per-campus rather than system-wide — `uniqueWith: ["campus_id"]` renders `UNIQUE (campus_id, course_number)`, still named `UQ_course_course_number` (the naming scheme didn't need to change). The mutual-exclusivity rule is checked at both layers (JSON Schema, then the generator, same belt-and-suspenders pattern as identity/nullable); a `uniqueWith` entry naming a nonexistent or self-referential column is checked only in the generator, since JSON Schema can't practically cross-reference sibling array entries by name.
- **Table/column `comment` text renders as calls to `utils.set_table_comment`/`utils.set_column_comment`.** SQL Server has no ANSI `COMMENT ON` (unlike Oracle/Snowflake); those procedures set the comment as an `MS_Description` extended property — the name SSMS and most third-party schema-documentation tools already read — idempotently. Comments are emitted as their own batch, after tables and foreign keys, since the target object has to exist first. Quote characters in comment text are escaped (doubled) for the T-SQL string literal — tested directly with a comment containing a `'`. This generator originally emitted raw `sys.sp_addextendedproperty` calls directly; it was switched over once the `utils` schema existed (see below), so the exists-check-then-add-or-update branch lives in exactly one place.
- **A `utils` schema for reusable database tooling, kept separate from `els`.** Its first inhabitants are `utils.set_table_comment` / `utils.set_column_comment`, idempotent wrappers around a shared internal engine procedure (`utils.set_extended_property`, does the existence checks and the add-vs-update branch once) rather than duplicating that branch in two near-identical procedures. `generate_full_schema.py` now calls these instead of raw `sys.sp_addextendedproperty` — which means the generated `els_full_schema.sql` has a real prerequisite: `utils` must be deployed (`-Schema utils`) before the generated script will run. That's documented (component README/CLAUDE.md, and a header comment in the generated file itself), deliberately not enforced by a guard-check inside the generated SQL.
- **Neither `utils` nor `els` has an explicit `CREATE SCHEMA` migration.** Both rely on Flyway's `createSchemas` setting, confirmed (via Flyway's own documentation) to default to `true` — Flyway creates any schema named in a run's `-schemas` argument that doesn't already exist, before running that schema's migrations. Worth knowing explicitly rather than assuming, since the opposite default would have required an extra migration in both schemas.

## How other components should use this

- `els-data-model`'s JSON entity definitions now feed `scripts/generate-full-schema/` directly — a real cross-component dependency. Changing that JSON's shape is a breaking change for this component's generator.
- Actual Flyway migrations under `migrations/els` are still hand-written; the generator produces a full-state *reference* for comparison, not migrations themselves. That mapping (diff against `full_db_model/current` → next migration) remains a not-yet-defined workflow.
- Anything that needs to run against the actual SQL Server database (seeding, further tooling) should go through `config/` for connection details rather than inventing its own config mechanism. The schema generator is the exception — it never touches a live database, so it needs no config at all.
- Seed-data import (turning `els-data-model/data/*.json` into `INSERT` statements) is explicitly out of scope for this generator and is expected to be a separate tool.

## Deployment

`scripts/Invoke-ElsMigration.ps1` wraps `flyway migrate`/`info`/etc. Requires the Flyway CLI on PATH and a local `config/config.json` (copied from `config/config.template.json` and filled in) — see the Flyway install/config guidance already captured in this project's chat history for setting up Flyway itself against SQL Server.

`scripts/generate-full-schema/` needs no deployment or connection config — it only reads local JSON and writes a local `.sql` file.

## Status

Folder structure and tooling scaffolded. Flyway wrapper smoke-tested (JDBC URL construction, named-instance handling, per-schema config lookup for both `utils` and `els`, an unknown-schema error listing the known ones, the mandatory `-Schema` parameter's prompt/fail behavior, and error paths for missing config/missing Flyway, all verified with a stubbed `flyway` executable). `migrations/utils` now has its first three repeatable migrations (`utils.set_extended_property`, `utils.set_table_comment`, `utils.set_column_comment`) — T-SQL syntax checked with `sqlfluff` (`--dialect tsql`), no unparsable sections; not yet run against a real SQL Server (none available in this sandbox), so live idempotency behavior is unverified beyond code review. `migrations/els` still has only the `R__placeholder.sql` no-op. No CI wired up yet.

`generate-full-schema` was tested directly, not just written: ran twice back-to-back against the real Campus/Course model and confirmed byte-identical (MD5-matched) output; confirmed `--check` correctly reports "up to date" on a clean model and "drift" against a changed one; added a synthetic third entity (`Classroom`, alphabetically between `Campus` and `Course`) and confirmed it was inserted between them while the `Campus` and `Course` `CREATE TABLE` statements stayed character-for-character identical to before; and confirmed clear error messages for a missing model directory and an entity failing schema validation. After switching its comment output to call the `utils` procedures, the full regression suite (byte-identical re-run, `--check`, synthetic-entity insertion including a quote-escaping check) was re-run against the new output, not just eyeballed.
