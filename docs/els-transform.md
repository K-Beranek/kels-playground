# Review: eLearning System Transformation (`els_transform`)

## What it is

A [dbt](https://www.getdbt.com/) project that transforms `els-database`'s raw `els` schema into a dimensional model — dimension and fact tables — for reporting/analytics. Scaffolded via `dbt init`; two example models exist so far (`stg_els__campus`, `dim_campus`), authored directly rather than generated by any tool.

## Key decisions

- **Same SQL Server instance as the source, not a separate warehouse (e.g. Snowflake).** dbt only transforms data already sitting in one database — it has no mechanism to move data between platforms itself. Targeting Snowflake would have required a separate extract/load component first, since the source data lives in SQL Server; targeting the same instance (a new schema) needed no new infrastructure. A real trade-off either way: this path practices `dbt-sqlserver` end-to-end on a platform already used elsewhere in this repo; the Snowflake path would have practiced dbt's best-supported, most realistic setup, at the cost of a whole extra component before any transformation could run at all.
- **`dbt-sqlserver` (the `dbt-msft` community adapter), not dbt's Fusion engine.** Checked directly rather than assumed: at the time of this decision, Fusion's supported adapters were Snowflake, BigQuery, Databricks, and Redshift — all still "Preview" — with no SQL Server support. This also ruled out dbt Labs' own official VS Code extension, which requires Fusion regardless of whether its optional registration is completed; `sqlfluff` with its `dbt` templater fills the editor-linting gap instead, since it renders Jinja through the real project via classic dbt-core and has no dependency on Fusion.
- **`.sqlfluff` lives in `els_transform/`, not the repo root.** It's configuration for this dbt project specifically — its `project_dir`/`profiles_dir` settings are simplest when it sits next to `dbt_project.yml` — and a repo-root config would technically also apply to `els-database`'s plain, non-templated T-SQL files, which sqlfluff's `dbt` templater has no business touching.
- **Folder/project name uses underscores (`els_transform`), unlike every hyphenated sibling component.** A dbt project's `name:` must be a valid identifier — hyphens aren't allowed — so the folder follows the project name rather than this repo's usual hyphenated convention. Not an inconsistency; a constraint from the tool.
- **No committed `profiles.yml` or `profiles.template.yml` yet.** Connection details are entirely local (`~/.dbt/profiles.yml`), consistent with this repo's secrets rule — but unlike `els-database/config/config.template.json`, there's currently no committed template showing a future clone what shape is expected. A gap worth closing once the adapter-specific connection keys are settled, not something to guess at speculatively.
- **Orchestration deferred, given a local-only SQL Server.** GitHub-hosted Actions runners can't reach a database on Karel's own machine. The planned path is manual `dbt build` while models are actively being built, moving later to a self-hosted GitHub Actions runner on that same machine — keeps CI defined as code, matching this repo's GitHub-Actions default, without relocating the database or paying for dbt Cloud (which wouldn't help here either, for the same reachability reason).

## How other components should use this

- Reads `els-database`'s deployed `els` schema (`els.campus`, `els.course`, ...) as dbt **sources**, declared in `models/staging/_staging__models.yml` — never queried directly without being declared there first.
- Does not read `els-data-model` at all, unlike `els-database`'s `generate-full-schema`. The star schema's shape is designed directly against the deployed relational schema, not derived from the same JSON entity definitions `els-database` generates from.
- The target schema for `dim_*`/`fct_*` tables is whatever `profiles.yml` (and any per-model `+schema:` override) resolves to — not yet finalized or documented, and subject to the `generate_schema_name` concatenation gotcha noted in this component's own `CLAUDE.md` once schema separation is actually needed.

## Status

Scaffolded via `dbt init` (2026-08-31): standard folder layout, `dbt-sqlserver` adapter, `.sqlfluff` configured for the `dbt` templater. Two example models exist — `models/staging/stg_els__campus.sql` (a thin cleanup view over `els.campus`) and `models/marts/dim_campus.sql` (selects from the staging model) — both hand-authored, both compiled and run successfully against a live database (`target/manifest.json`/`run_results.json` present from a real run). No `packages.yml` (e.g. `dbt_utils`) yet. No `profiles.template.yml` yet. No CI wired up yet.
